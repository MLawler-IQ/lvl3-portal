## 1. What shipped

### Onboarding is one surface, and it records where every value came from

Three surfaces used to configure a client and **nine columns were writable from
two of them with nothing arbitrating**. Approving an interview silently
overwrote hand-typed settings — the exact failure `lib/onboarding/discover.ts`
says in its own header that it exists to prevent.

Setup is now the primary content of the client page with settings beneath it,
and every one of the nine shared fields shows its source, confidence and
evidence. A hand edit in settings is recorded as `source: 'manual'` and survives
a later interview re-run.

The load-bearing rule, in `isFilled`:

| source | counts as answered |
|---|---|
| `auto` + high | yes — read from the agency's own Google account |
| `auto` + low | no — a pre-filled suggestion |
| `interview` | yes |
| `context` | **never, at any confidence** |
| `manual` | yes |

`context` is a value a model inferred from a transcript. It carries its quote, it
shows in the UI, and it cannot move a session to `ready_for_review`. A model
reading a transcript is guessing however fluently it phrases the guess.

### The slot set went from 19 to 12

Nine of the nineteen required slots promoted to no column and were read by
nothing. Requiring them meant an interview could not finish without answers
nobody consumed. Now **3 are required** — the ones that gate a real integration —
and the rest are asked but non-blocking. The seven cut slots survive as
`LIBRARY_TOPICS`: still worth capturing, no longer a gate.

A verifier caught the trap this opened: discovery seeds exactly those three
required slots, so a brand-new session could show **"100%"** before anyone asked
a question. `pct` still answers "can this be approved"; `totalPct` answers "how
much do we know", and the review pane shows the second.

### Zoom finds the client's calls

You type a domain — or nothing, and it uses the client's own website — and it
searches the last 180 days of cloud recordings and AI Companion summaries,
matching by participant email first, then meeting topic, then attendee names,
then summary text. Ported from `iiq-preextract`.

Every call shows **why it matched**, because "participant bridget@airworks.com"
is a much stronger claim than "attendee Matt Lawler".

### The context library

`client_context_items` holds transcripts, summaries, emails, notes, pages and
audit runs, **kept for the life of the client**. `source_ref` is the idempotency
key, so re-importing the same call updates one row rather than appending a second
copy — duplicate transcripts would let the extractor "corroborate" a value
against what is really one conversation.

### Clients can be archived, and deleted

Archiving hides a client everywhere and touches nothing. Permanent deletion is
gated behind archiving, shows what it will destroy, and requires typing the name.
Nine tables cascade off `clients.id`; storage cascades from nothing at all, so
the delete path clears the buckets explicitly.

### The audit runs from the portal

`/tools/audit` takes a Sitebulb export, runs the pipeline, stores the run in
`audit_runs`, and writes the rendered report into the context library as
`kind: 'audit_run'`. The export goes to a private `audit-exports` bucket via
signed upload URLs — bytes never cross a serverless request, so Vercel's 4.5 MB
body cap does not apply.

The export is **kept**, not deleted after the run. A stored finding is a claim
about an artifact, and the rubric behind it is known-incomplete and changes slice
by slice — delete the export and every past run becomes a claim about something
nobody can look at again. Delete-on-success is also inverted: the export anyone
wants to re-read is the one that failed.

### GBP answers for the first time

The `gbp` station was hardcoded `unavailable`, so LOCAL-003 and LOCAL-016 were
permanently `not_run`. It is now wired and emitting.

## 2. The bugs that mattered

Ordered by how quietly they would have failed.

**LOCAL-016 fabricated a FAIL.** The Business Information API returns
`serviceArea` only for a service-area business, so every storefront client yields
`serviceAreas: []` — and an empty declared set made "outside the service area"
mean "anywhere but the business's own city". Reproduced through the real `CHECKS`
registry: `fail`, `affectedUrls: 2`, on a client with no data. A
`verticalCritical` fail with a plausible magnitude, derived from a field the
profile never populates. Now `not_run` with a reason, pinned by an exhaustive
test crossing three anchors against four declared sets.

**The audit upload could not have worked on any input.** It sent `Uint8Array`
across a Server Action, where Next's Flight encoder reaches `getIteratorFn`
*before* its plain-object check. Typed arrays have `Symbol.iterator`, so it
silently returns `Array.from(value)` and raises nothing. The server received
`number[]`, `TextDecoder` threw, `runGuarded` turned that into a station failure,
and every crawl-backed check would have reported `not_run` on every run forever.
The stored run would have been perfectly honest and empty of signal.

**The manual-override protection was dead code.** The read side was wired and the
write side never existed — `ClientSettingsForm` carried a detailed comment
describing the write; `updateClient` never did it. 185 lines of passing tests
covered a path that could not occur.

**Archiving a client broke client creation.** The slug collision check read the
visible client list, which now excluded archived clients — but the unique index
covers every row. Archive "Tornado HVAC", recreate it, and the insert dies. The
error was also unreadable, because thrown server-action errors are redacted in
production.

**Approving an interview looked like it saved nothing.** It saved everything.
`ClientSettingsForm` seeds 23 `useState` values from props and a `useState`
initialiser runs once, so `router.refresh()` handed it fresh props it ignored.
The tell was that the provenance badge and the radio disagreed about the same
field — the badge reads props and was right, the radio read state and was stale.

**Retention was scheduled and never ran.** `cleanup_old_tool_data` was created in
June with a 90-day window and a schedule conditional on `pg_cron`, which was not
enabled. Four months of data accumulated against a limit nothing enforced, which
turned "enable the scheduler" into a destructive act: the first run would have
deleted 19 of 22 content-engine runs and 110 of 157 topics. Widened to 365 days
*before* anything could fire.

## 3. The pattern worth remembering

**Three times, a change compiled, passed its tests, and was never invoked.**

The mechanisms:

- **Optional parameters make "unwired" compile.** `priorContext?: unknown` was
  optional so it could land before its caller — and the caller never came.
  TypeScript actively helped.
- **Unit tests construct their own inputs.** A test proving `buildClientUpdate`
  correct given a hand-made `priorContext` says nothing about whether production
  produces one. Two independent claims, one checked.
- **Registries are runtime lookups, not type-level links.** `/tools/audit` existed
  and appeared on no page, because the hub renders only `registry.ts` manifests.

They stay invisible because everything else in this codebase fails loudly. An
uninvoked feature produces no exception, no log, no red test. **Absence has no
error**, and silence reads identically to "fine".

It is also the same disease as the fabricated pass this codebase is built around.
A fabricated pass is a check claiming it ran when it did not. An unwired feature
is a codebase claiming it shipped when it did not. Both are unbacked claims
wearing the shape of success.

### What was done about it

**Four optional parameters became required** — `priorContext`, `existingSlugs`,
`service_context`, and discovery's client identity. Each existed so callers could
compile. Making them required surfaced **15 call sites** immediately.

**`tests/unit/tool-reachability.test.ts`** asserts every tool route has a registry
manifest and every shipped manifest has a route. Ten lines. It found **five real
defects on its first run** — `/tools/audit` unregistered, and four manifests
pointing at routes that do not exist, three of which are legitimately
`coming-soon` and now exempt on a *verified* basis (the hub renders those with
`href="#"` and `pointer-events-none`, so they cannot navigate).

The lesson is not "review harder". It is **make the compiler care**.

## 5. Where it stands

### Working
Onboarding with provenance · Zoom import · context library · archive and delete ·
`/tools/audit` end to end · GBP station emitting · brand terms and competitors
pre-filled at low confidence for confirmation.

### Built, not wired
- **`lib/geo/distance.ts`** — geocoding, haversine, drive distance. Typed
  failures, a precision scale, and a refusal to return a number it cannot stand
  behind.
- **`lib/connectors/gbp-reviews.ts`** — v4 reviews and media.

### The gap that matters
**The §3 trap is still open.** A profile that *declared* Orange County still
passes on Orange County pages served from Sherman Oaks — the documented pilot P1.
Both instruments exist; neither is callable from a check, because `evaluate` is
`(stations: StationBundle) => Finding` — synchronous — and `GbpProfileRecord` has
nowhere to put a distance. The honest place to measure is the station, which is
already async. That is a design change, not a wiring one.

LOCAL-016 went from *fabricating a fail* to *honestly not_run*. That is a real
improvement and it is not yet the check its rubric describes.

### The audit's real shape
Eight of 80 rubric rows are implemented. The ceiling for full automation is 44 —
the other 36 are `assisted` by design. Six of the eight checks read only the
Sitebulb export, which is produced outside the portal.

Nothing connects onboarding context to the audit. `service_context` is read by no
station, check or scorer. That is schedule rather than neglect — the synthesis
step designed to consume it is slice 7 of 7 — but it means the twelve slots feed
nothing today.

### Cheapest next work
- **28 sitebulb checks** — data already parsed and in the bundle.
- **A `semrush` station** — unblocks AUTH-001/002/003 against a connector already
  in production. Would also prove the station pattern generalises past Google.
- **A `pagespeed` station** — two more rows, connector already wired.

### Open questions
- The rubric does **almost no keyword analysis** — two of 80 rows. For an agency
  selling organic growth that is a conspicuous hole, and it is a rubric decision
  rather than an API problem: Semrush, Keywords Everywhere and GSC are all
  connected.
- `pg_cron` is still off, so nothing purges on a schedule. Deliberate.
- Neither Zoom call had a cloud recording, only thin AI summaries. Turning on
  cloud recording would do more for extraction quality than any code change.
